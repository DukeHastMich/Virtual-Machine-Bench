PERFORMANCE BRICK 14 — VGA/VRAM CLOCK-BATCH MEMORY CYCLES
=========================================================

WHY THIS ONE LOOKS LIKE A REAL WINDOWS-SPECIFIC SMOKING GUN
-----------------------------------------------------------
Windows is using Microsoft's generic VGA driver, not the S3 accelerated driver.

On the current bus, EVERY mapped-memory byte to a clocked device does this:

    SynchronizePendingTime(MemoryAccess)
        -> MachineClock FlushPendingBatch
        -> HardwareBus.AdvanceTime(...)
        -> every registered clocked device advances

    device.ReadMemoryByte / WriteMemoryByte

    NotifyTimingTopologyChanged()

That means a generic VGA software rasterizer pounding A0000h can flush the
ENTIRE motherboard/device clock batch once per VGA byte.

A DOS/HIMEM RAM workload does not hit that path, which matches the observed
shape very well:
    HIMEM can run much faster
    early Windows can burst far above realtime
    steady Program Manager/GDI collapses to a 2–14% bounce

WHAT CHANGED
------------
HardwareBus now supports a per-memory-cycle timing classifier for clocked
mapped-memory devices.

DiamondStealthPro928 classifies its memory windows as follows:

  Option ROM:
      no clock synchronization
      no timing-topology change

  Ordinary VGA legacy VRAM aperture:
      no clock synchronization while the enhanced engine is idle
      no timing-topology change

  S3 linear VRAM window:
      same as ordinary VRAM

  S3 MMIO / PIX_TRANS / enhanced-register aliases:
      synchronization REQUIRED
      timing topology may change

  VGA/linear VRAM while enhanced graphics engine is BUSY:
      synchronization REQUIRED before the CPU access
      because the CPU and engine share authoritative VRAM and ordering matters

WHY THIS DOES NOT MAKE VGA "ASYNC"
----------------------------------
The CPU still pays every modeled memory-cycle T-state and READY wait.

Pending physical machine time is still advanced by the same coordinated
MachineClock286, at:
  * real clock/wake deadlines
  * guest I/O accesses
  * timing-sensitive MMIO accesses
  * the normal bounded clock-batch ceiling
  * end of slice

A later guest status-port read synchronizes pending time BEFORE reading the
device, so 3DAh/retrace status still sees the correct emulated time.

The optimization only removes an unnecessary implementation rule that said:
"because this object ALSO contains a clocked S3 engine, every byte of passive
VRAM storage must advance every clocked device immediately."

ENGINE/VRAM ORDERING IS PRESERVED
---------------------------------
If the enhanced S3 engine is running, CPU VGA/linear VRAM accesses remain
synchronization points.  This prevents host batching from moving CPU VRAM writes
ahead of graphics-engine work that should have happened first.

NOT CHANGED
-----------
* CPU T-state accounting
* READY/wait states
* A20 / physical decode
* mapped-memory routing
* VGA latches / read modes / write modes / map mask / set-reset / logical ops
* S3 engine 40 MHz timing
* PIX_TRANS timing
* S3 command FIFO/BUSY state
* VGA/S3 register semantics
* host presentation worker
* IRQ behavior
