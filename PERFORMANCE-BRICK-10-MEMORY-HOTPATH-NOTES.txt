PERFORMANCE BRICK 10 — SINGLE-PASS LOCAL MEMORY DECODE

Goal
----
Remove repeated host decode work from the hottest CPU path without changing
motherboard decode, READY timing, ROM protection, A20, or physical bus cycles.

What the bridge already knew
----------------------------
For an ordinary local byte access, NeatMotherboardBridge286 already:

  1. normalizes the 24-bit physical address / A20 / reset-ROM alias;
  2. checks whether a mapped device can own the page;
  3. classifies the remaining local target as DRAM / system ROM / open bus;
  4. uses that exact target to apply NEAT READY timing.

The old final read/write then called NeatMemoryController286 again, and that
method classified the SAME normalized address a second time.

Aligned 16-bit local cycles were worse: the bridge classified both bytes to
prove that a direct 16-bit cycle was legal, then ReadLocalWord/WriteLocalWord
classified the bytes again.

After
-----
The bridge passes its already-established target into:

  ReadLocalByteNormalizedKnownTarget
  WriteLocalByteNormalizedKnownTarget
  ReadLocalWordNormalizedKnownTarget
  WriteLocalWordNormalizedKnownTarget

Compatibility wrappers remain for any other caller that does not already own a
decode result.

This is not a RAM shortcut.  The motherboard still performs exactly one real
decode decision for the transaction, and THAT decision controls both READY and
the final backing-store action.

Preserved
---------
* programmable mapped-memory/device precedence
* NEAT shadow / ISA-hole selection
* A20 masking
* 24-bit physical wrap
* high reset-ROM alias
* ROM read-only behavior
* open-bus FF reads / ignored writes
* local DRAM writes and legacy-mirror behavior
* CPU/DMA bus ownership
* byte vs aligned-word bus-cycle count
* Brick 3 NEAT READY cache
* Brick 5 static port-decode optimization

High ROM alias micro-optimization
---------------------------------
NormalizePhysicalAddress previously recalculated the top-of-16-MiB system-ROM
alias start from _romStartInBed on every physical memory access.

That boundary changes only when LoadSystemRom() installs a ROM.  It is now
stored as _highRomAliasStartInBed and updated at the same time as _romStartInBed.

The reset fetch still resolves the high ROM alias BEFORE the compatibility A20
gate, exactly as before.

File changed
------------
HardwareBus.vb

Expected impact
---------------
This path is used by instruction prefetch, stack traffic, ordinary data access,
and much of Windows' memory traffic.  The gain may still be modest because
actual array accesses and CPU decode dominate, but unlike port Brick 5 this
eliminates duplicated work from nearly every local memory transaction.
