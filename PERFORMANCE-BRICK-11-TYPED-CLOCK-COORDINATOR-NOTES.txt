PERFORMANCE BRICK 11 — TYPED MACHINE-CLOCK COORDINATOR

Why this exists
---------------
One of the hottest remaining host operations was not a guest device at all.

MachineClock286.RunSlice() built four capturing lambdas on EVERY host slice:

  refreshDeadline
  flushPending
  topologyChanged
  timeAdvanced

plus a halted-step Func.

Processor286 then called:

    timeAdvanced.Invoke(_lastInstructionTStates)

after essentially EVERY retired instruction.

The callback itself is architecturally required: motherboard time must become
eligible for a flush at the same instruction boundaries, wake deadlines, bus
synchronization points, and batch ceilings as before.

The expensive part was representing that invariant through compiler-generated
closure objects and Action/Func delegate dispatch.

What changed
------------
MachineClock286 is NotInheritable and now owns one reusable active-batch state
frame.

Processor286.RunForTStates receives the concrete MachineClock286 coordinator and
calls:

    AdvanceCpuTStatesInBed(tStates)

at the EXACT SAME places where it previously invoked timeAdvanced:
  * bus HOLD idle steps
  * NMI entry timing
  * maskable interrupt entry timing
  * HLT fast-forward
  * every normal retired instruction

HLT asks the same concrete coordinator for HaltedStepBudgetInBed().

HardwareBus also stores one typed ITimeBatchSynchronizer286 instead of two
Action delegates.  Port/MMIO/time-topology synchronization points are unchanged.

Preserved algorithm
-------------------
The code was intentionally moved nearly statement-for-statement from the old
closures into coordinator methods:

  pendingBatchPicoseconds += T-states * ps/T-state
  refresh wake deadline when dirty
  flush at next spontaneous wake
  else flush at maximum batch ceiling
  synchronize before guest I/O/MMIO where required
  advance HardwareBus by the same pending interval
  recompute next wake after every flush
  retain HLT fast-forward semantics
  retain 64-T-state conservative fallback for unclassified devices
  subtract the same advanced physical time from scheduler debt

Runtime diagnostic counters, when enabled, are copied from the new batch-state
fields with the same reason classification.

Guest-visible behavior NOT changed
----------------------------------
* processor instruction timing
* location/frequency of instruction-boundary time accounting
* device wake deadlines
* PIT / PIC / DMA
* IRQ timing
* I/O or MMIO synchronization
* HLT behavior
* READY timing
* scheduler debt accounting
* turbo/20-vs-25 MHz ratios

This is deliberately NOT "batch more instructions."  It batches exactly as much
as the old code.  It only removes host closure/delegate machinery around the
existing batching rules.

Files changed
-------------
  ProcessorCore.vb
  MachineTiming.vb
  HardwareBus.vb

Patch stacking
--------------
* ProcessorCore.vb is based on Brick 2: PIC INTR + prefetch ring preserved.
* HardwareBus.vb is based on Brick 10: NEAT READY cache, static port decode, and
  single-pass local-memory decode preserved.
* MachineTiming.vb is the diagnostics-off baseline; no later performance brick
  changed it.

Risk / build gate
-----------------
This is a broader internal refactor than Bricks 5-10, although its algorithm is
intended to be bit-for-bit equivalent at the machine boundary.

Build/boot it as its OWN gate.  Compare DOS and Windows before applying any
later brick.  If the compiler finds an accessibility/signature issue, fix this
brick only before continuing.


Accessibility note
------------------
ITimeBatchSynchronizer286 is declared Public because the public MachineClock286
implements it.  The installation entry on HardwareBus remains Friend, so this
does not create a guest-visible API or broaden runtime ownership; it only avoids
a VB accessibility mismatch at compile time.
