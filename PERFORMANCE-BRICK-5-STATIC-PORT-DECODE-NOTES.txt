PERFORMANCE BRICK 5 — STATIC I/O PORT DECODE FAST PATH

Why this target
---------------
Windows touches a lot of I/O ports: PIC, PIT, 8042, RTC, chipset index/data,
UARTs, IDE, FDC, VGA/S3, etc.

HardwareBus already compiles a 65,536-entry PCB candidate table at machine
construction time, but every actual IN/OUT still called HandlesPort() on the
selected fixed-decode device.

Worse, an ordinary CPU I/O cycle asks the port fabric once to determine whether
the cycle uses motherboard-local or AT-bus READY timing, then the actual
ReadByte/WriteByte path resolves the port again.

This brick does not remove either physical phase.  It makes the common fixed
decode lookup nearly free.

What changed
------------
A second precompiled table records ports which have EXACTLY ONE candidate and
that candidate has immutable decode wiring:

    _directStaticPortDevices(port)
    _directStaticPortUsesAtBusTiming(port)

For those ports:
  * PortUsesAtBusTimingInBed() is one array lookup + Boolean return.
  * ResolvePortDevice() is one array lookup.
  * HandlesPort() is NOT called again at runtime.

This covers ordinary fixed motherboard devices and fixed-base devices such as
PIC/PIT/8042/RTC/UART/IDE/FDC/LPT.

Board-integrity rules
---------------------
Programmable decoders NEVER use the shortcut.

Any device implementing IPortDecodeCandidateProvider is considered dynamic.
Current examples:
  * Diamond Stealth Pro 928 (setup/address/enhanced decode can change)
  * NE2000 ISA card (jumper/base selection)

If a port has more than one possible physical candidate, the direct entry is
discarded and the old ordered route walk remains intact.

Therefore:
  * registration/decode priority is unchanged;
  * programmable chip-select changes still take effect on the very next cycle;
  * collision behavior is unchanged;
  * open-bus behavior is unchanged;
  * READY timing class is unchanged.

This is equivalent to a PCB trace whose destination is known permanently at
assembly time.  It does not bypass a device or invent a host-only port result.

Not changed
-----------
  * port-access clock synchronization
  * per-device ReadPort/WritePort behavior
  * PIC/PIT/DMA
  * UART / Microsoft serial mouse protocol
  * S3/NE2000 dynamic decoding
  * IDE/ATAPI
  * CPU timing
  * memory decode
  * scheduler policy

File changed
------------
  HardwareBus.vb

Patch stacking
--------------
This HardwareBus.vb is based on Performance Brick 3, so the NEAT READY cache is
preserved.  Brick 4 changes only DiamondStealthPro928.vb and is unaffected.
Brick 2 changes ProcessorCore.vb and is unaffected.

Measurement
-----------
Use the same Windows workload and DOS prompt.  This one is intentionally a
broad, low-risk I/O hot-path optimization; if it barely moves the meter, keep it
only if behavior is stable and continue down the Windows-touch list.

Mouse note
----------
The serial-mouse host path already coalesces raw host motion outside the machine
gate and hands counts over only at a machine boundary.  The actual mouse then
runs through its 25-ms physical sampler, 1200-baud serial framing, UART RX, and
IRQ4.  That architecture looks sane, so port dispatch is the cleaner first
mouse/Windows-adjacent optimization.
